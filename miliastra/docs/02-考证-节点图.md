## 0. 结论先行（三条会改方案）

1. **没有"每帧执行"节点。** 服务端节点图**全部是事件驱动**的；
   唯一的周期驱动是【定时器】，**最小间隔 0.03 秒（≈33 次/秒）**。
2. **路径路点上限 50 个**（《编辑项范围限制》）。本项目导出的槽位数超了 ——
   `cross-return` 111、`endless` 82、`spiral-inner` 60（`spiral-outer` 已于 2026-09-25 删除） ✗
3. **自定义变量支持 列表 / 字典 / 结构体，而且读写是全局作用域** ——
   「实体可以读取、修改**任意实体**上的自定义变量」。这正好用来存"球的状态"。

## 1. 执行模型

- 《基础概念》(mhk23ora1wom)：「**服务端节点图均是事件驱动的，即服务端节点图执行流的起点
  一定是事件节点**」；「技能节点图不是事件驱动的，而是有一个固定的*节点图开始*节点」；
  「本地过滤器节点图只有运算流……没有起点」。
- 帧语义只有一句：「**所有节点图的执行流可以认为是在同一帧顺次执行的**
  （在不考虑性能问题导致执行流延迟的情况下）」—— 这只说明同帧内顺序，**没给 tick 频率**。
- 唯一近似"持续跑"的：《其它节点》说造物状态决策/状态节点图「**会持续执行**」，
  但归属端是**客户端**，且只服务复杂造物 AI。
- **唯一的周期驱动是定时器**：《定时器》「定时器序列应是一组从小到大排列的、
  以秒为单位的时间点（**最小间隔为 0.03 秒**）」，到点触发一次【定时器触发时】事件。
  《全局计时器》只在倒计时结束时发一次事件。
- 「全文检索"每帧"仅命中 1 处，且是 BBS 用户帖；官方与派生正文中**不存在 tick / update / 每帧执行节点**。」

## 2. 节点图种类与挂载

| 类型 | 挂载对象 | 触发时机 | 端 |
|---|---|---|---|
| 实体节点图 | 实体/元件（详情页-节点图） | 事件驱动；生命周期跟随实体 | **服务端** |
| 单位状态节点图 | 单位状态 | 事件驱动（例：持续攻击附近的火环状态） | **服务端** |
| 职业节点图 | 职业配置（仅超限模式） | 职业切换时前一个失效 | **服务端** |
| 道具节点图 | 道具配置 | 道具相关事件 | **服务端** |
| 技能节点图（角色/造物/角色操控） | 自定义技能-动画编辑-时间轴-**节点图事件轨道** | "运行到挂载了技能节点图的时点时" | 客户端 |
| 造物状态节点图 / 造物状态决策节点图 | 复杂造物-特化配置 | 决策图"按顺序唯一执行"、持续执行 | 客户端 |
| 本地过滤器节点图（布尔/整数） | 各组件内引用（如**命中检测组件-命中规则**） | "在每次命中发生时，执行一次" | 客户端 |

- 《复合节点》：「复合节点**只能**在服务器节点图中使用，无法在客户端节点图中使用」。

## 3. 服务端 vs 客户端

- 「实体节点图、单位状态节点图、职业节点图和道具节点图的逻辑在**服务端**运行……
  技能节点图、造物状态节点图和本地过滤器节点图都是在**玩家本地**运行」。
- 客户端 -> 服务端：【通知服务器节点图】，「支持携带**三个字符串参数**」，
  在服务端触发【技能节点调用时】事件 ✓
- 服务端 -> 客户端：**没有明文的数据下发节点** ✗
  最接近的是《自定义变量》「**仅有配置在组件中默认创建的自定义变量才会被同步至本地**」✓
- 边界例：《千星沙箱》FAQ「【销毁时】事件需要挂载在【关卡实体】上……
  因为实体监听不到其他实体销毁」。
- 《事件节点》(derived) 收录的 **66 个事件，归属端全部是"服务端"** ✓

## 4. 变量系统（★ 这是移植的支点）

- 每个实体可存自定义变量，**支持列表与字典**：整数/浮点/字符串/布尔/三维向量/实体/GUID/
  元件ID/配置ID/结构体，及各自的列表类型与"所有字典数据类型" ✓
- 作用域原文：「自定义变量的**读和写拥有全局的作用域**，即实体可以读取、修改
  **任意实体**上的自定义变量」；「生命周期跟随组件（同理也跟随组件挂载的实体）」✓
- 限制：
  - **本地节点图只能"读取"自定义变量** ✗（操作项：服务端读/写/监听、本地读）
  - 节点图变量「**仅在服务端节点图中可用**」「仅在定义该变量的节点图内可访问」
- 坑：容器类型是**引用传值**，「对容器类型自定义变量的操作会导致自定义变量的值发生变化」，
  且这类修改**不触发**【自定义变量变化时】事件 ✗

## 5. 循环与条件

- 条件：《流程控制节点》**只有【双分支】和【多分支】**，多分支"仅支持整数或字符串" ✓
- 循环（《执行节点》）：【有限循环】（起始值到终止值，每次 +1）、【跳出循环】、
  **【列表迭代循环】**（入参"迭代列表"、出参"迭代值"），客户端侧另有【遍历实体列表】✓
- **没有 while / 无界循环** ✗

性能相关（**没有任何一条直接写"不适合高频逻辑"**）：
- 《负载计算功能》：静态负载「**并不能评估节点图等动态运行逻辑带来的负载消耗**」；
  动态报告会列出「**异常节点图**」及负载占比，试玩时"每一秒进行数据统计" ✓
- 《负载优化》：造物「**超出范围降频运行**（默认开启）……超出角色一定范围将在该角色端**降频**」✗
- 《命中检测》：CCD「**有较高的性能开销，仅推荐在适用情景（高速运动且需要精确命中）**下使用」✓
- 《风险检查功能》只查"不建议的配置/隐藏规则"，且"一般是**数据上的错误**"，不是性能告警。

## 7. 文档明确没说的

1. 服务端/客户端 **tick 频率（Hz）** 从未给出。
2. 没有 tick/update/每帧节点；索引里提到的【**等待帧**】节点在正文中**检索不到**。
3. 没有"不适合高频逻辑"的明文，也没有单节点耗时 / 每帧节点预算。
4. 0.03 秒只是定时器的**最小间隔**，**没说**它是"建议的最快逻辑频率"。
5. 字典/列表的单容器容量未单列（只有通用的"运行时列表元素最大 1000"）。
6. 联机多端下的时序一致性、并发写冲突规则完全未涉及。
7. 客户端->服务端只支持 **3 个字符串**；服务端->客户端主动下发通道未成文。

## 8. 对"每秒几十次的祖玛实时规则"的判断

按文档可确证：**纯靠节点图自循环做 30Hz 逻辑，只有【定时器】一条路（最小 0.03 秒 ≈ 33 次/秒）**，
且对动态负载只提供"超标预警"，**不提供性能保证或频率上限承诺**。

同时官方把"**持续运动**"与"**碰撞判定**"分别交给引擎侧的**路径 / 基础运动器**与
**命中检测组件**（触发类型可选"重复触发 + 触发间隔"）✓
节点图在官方举例中承担的是**事件 -> 条件 -> 结果**的离散逻辑 ✓

所以"轨道前进 + 命中判定 + 成段消除"三者里：
- 前两者有**引擎原生承载**（沿路径运动、【路径到达路点时】、【命中检测触发时】）✓
- 节点图负责**状态与消除判定**是文档支持的做法 ✓
- 而"用节点图以每秒几十次驱动主循环"这一条，文档**既未否定，也从未承诺** —— 属于未覆盖区域，
  只能进游戏实测 ✗
